# Serena — setup, configuration, and conformance

What this plugin depends on, and where Serena's own behaviour constrains the
design. Serena-specific detail lives here; the fallback backend is
[cclsp-retirement.md](./cclsp-retirement.md).

## 1. The three per-project layers

A provisioned Serena project is three on-disk artifacts, written by three owners:

1. **`~/.config/serena/projects/<name>/project.yml`** — written by this plugin's
   descriptor. The project's language servers, paths, and ignore rules.
2. **`serena_config.yml`'s `projects:` registration** — written by Serena itself
   (`ruamel`, comment-preserving). **This plugin never writes it.**
3. **The instance conf plus its socket** — written by `serena-instance enable`,
   binding a project to a port.

A project is usable when all three agree. They drift independently, which is what
the drift reports in §5 exist to surface.

## 2. Project configuration is centralized

`serena_config.yml` sets

```
project_serena_folder_location: "<config>/serena/projects/$projectFolderName"
```

so every project's `project.yml`, cache, and memories live under
`<config>/serena/projects/<name>/`. Nothing is written into a working tree, and
no `.serena/` directory is created in any repo **by the MCP server path**.

Only `$projectDir` and `$projectFolderName` are valid placeholders;
`$SERENA_HOME` raises `SerenaConfigError` (see `_resolve_serena_folder_location`).
An absolute path is used because `SERENA_HOME` itself is not substitutable.

**Directory keying is on the basename of the project root, not on
`project_name`.** `serena project create /x/foo --name bar` writes
`projects/foo/` and puts `project_name: bar` only inside the file. Verified on
both 1.7.0 and 2.0.0; `projectDir()` in `src/codeintel/serena-project.ts`
depends on this.

**Fallback location.** `$projectDir/.serena` is the *fallback*: if a project tree
contains a stale `.serena/`, it takes precedence over the centralized path until
removed. Keep repo trees free of `.serena/`.

### 2.1 CLI litter caveat

`serena project health-check` and `serena project index` hardcode
`<project>/.serena/logs/` (`constants.py:9` `SERENA_MANAGED_DIR_NAME = ".serena"`,
`DEFAULT_PROJECT_SERENA_FOLDER_LOCATION = "$projectDir/.serena"`; call sites
`cli.py:810`, `cli.py:941`) and ignore `project_serena_folder_location`, so those
subcommands create a `.serena/` in the project tree despite centralization. The
MCP server path is clean. This is an upstream defect. Until it is fixed, avoid the
`serena project` subcommands in a working tree, or remove the stray `.serena/`
afterward, and keep the path out of any `.gitignore` decision by not creating it
at all.

## 3. Language-server selection

Language servers are selected per project, in
`<config>/serena/projects/<name>/project.yml`. Valid values are the
`LanguageServerId` enum in `solidlsp/ls_config.py` (**77 values** on 2.0.0),
whose `get_source_fn_matcher` is the authoritative extension table. Watch for:

- `json` covers `.json` and `.jsonc`; `toml` covers `.toml`. Both valid.
- `bash` matches only `.sh` and `.bash`. Dotfiles (`.bashrc`, `.bash_profile`)
  and `.conf` files are shell syntax but are **not matched by extension**, so a
  project full of them still needs `bash` listed to be correct in intent.
- `markdown`, `yaml`, `json`, `latex`, `toml` are experimental in Serena and are
  never auto-detected; they must be listed explicitly.

`src/serena-provision.ts` holds `EXTENSION_SERVERS`, the extension→server
table. It maps **51** servers; all 51 are valid 2.0.0 IDs (verified, §6). The
remaining 26 catalogue entries are 15 alternative backends for languages already
covered (`python_basedpyright/jedi/pyrefly/ty`, `php_devsense/phpactor/phpantom`,
`cpp_ccls`, `csharp_omnisharp`, `ruby_solargraph`, `typescript_vts`,
`julia_fatou`, `lua_emmylua`, plus the `angular`/`deno` umbrellas that need
npm/a CLI) and 11 languages deliberately unmapped (`ada`, `ansible`, `astro`,
`bsl`, `gdscript`, `groovy`, `lean4`, `matlab`, `msl`, `pascal`, `wolfram`). The
11 were already unmapped on 1.7.0 — pre-existing scoping, not upgrade drift.

### 3.1 Autogenerated configs cover one language only

Non-interactive autogeneration (`interactive=False`) enables only the
top-weighted language server for the languages it detects. A polyglot directory
is therefore covered only partially by an autogenerated `project.yml`. This is why
`serena-provision` exists: it writes a full multi-language configuration rather
than accepting the autogenerated stub.

## 4. The socket/unit layer

Serena runs behind a `systemd-socket-proxyd` shim: a `serena-mcp@<port>.socket`
accepts connections and a `serena-backend@<port>.service` runs the server bound to
loopback. The proxy exists for the reason in §4.1.

### 4.1 Serena cannot be natively socket-activated

Serena never reads `LISTEN_FDS`, and FastMCP builds `uvicorn.Config` with only
host and port — there is no file-descriptor inheritance path. So the socket
cannot be handed to the server; a `systemd-socket-proxyd` sits in front of it.
That transport detail is also why the plugin's architecture assumes an HTTP
endpoint per instance rather than stdio.

The backend needs a `WorkingDirectory`, which does **not** expand `${VAR}` in a
unit; that is why the unit's `ExecStart` is a `/bin/sh -c 'cd … && exec …'`
wrapper.

### 4.2 Idle TTL vs. memory

`--exit-idle-time` on the proxy reclaims the *entry point* when idle. It cannot
keep anything warm — which is the opposite of what a file-keyed router would want
(see [lsp-router-design.md](./lsp-router-design.md) §6). Read the value from the
unit files; a mismatch between the serena and fallback units is a bug.

### 4.3 Reclamation

Instances that are idle can be reclaimed by an operator-supplied prune job. The
plugin does not schedule one; the deployment decides the policy.

## 5. Disable / re-enable semantics

`serena-instance disable` deletes the instance conf (layer 3) but **leaves the
`project.yml` and the `serena_config.yml` registration** (layers 1 and 2).
Re-enable is therefore cheap — `serenaCreate` pre-checks `project.yml` and skips
`create` entirely.

Consequence: the `serena_config.yml` registry **only grows**, and
`serenaRegistryDrift()` (`src/codeintel/descriptors.ts`) surfaces the divergence
between the registry and the instance confs. It scans, never writes —
`serena_config.yml` is ruamel-owned, and re-serializing it destroys comments.

**As of 2.0.0 this is a deliberate policy, not a limitation.**
`serena project remove` now exists and cleanly removes a registration; on 1.7.0
it did not. The disable path keeps the registration because re-enable is then
cheap, not because removal is impossible.

## 6. Version conformance (1.7.0 → 2.0.0)

Upgraded 2026-10-15. Every field, directive, and API call this plugin depends on
was verified against a version-matched source. **No configuration change was
required to preserve functionality.**

### 6.1 What changed in 2.0.0

- Relicensed to **GPL-3.0-or-later** (SolidLSP stays MIT).
- `activate_project` now requires an explicit **`session_id`**; obtain it from the
  `initial_instructions` tool output (``Your Serena session id is `xxxxxxxx` ``).
  The MCP `initialize` result carries only a pointer to that tool. Our instances
  run `--context ide`, which **exposes** `initial_instructions` but excludes
  `activate_project` (single-project mode). This is the reason this plugin
  provisions projects through its own descriptor rather than asking the server to
  adopt a path at runtime.
- **One-language non-interactive autogen** (§3.1).
- `--context` accepts a custom YAML file path.
- New tool `replace_in_files`; `name_path` alias for `name_path_pattern`.
- Tool-call errors now surface explicitly at the MCP protocol level.
- New CLI subcommands: `project create`, `health-check`, `index`, `index-file`,
  `is_ignored_path`, `project remove`.

### 6.2 The version trap (upgrade procedure)

After upgrading Serena, **restart the backend units.** Lazy Python imports mean a
running pre-upgrade process loads new code from disk while holding old in-memory
state. Worse, pre-2.0.0 processes reported `serverInfo.version` as the **MCP SDK**
version (`2.2.0`) rather than Serena's — a bug 2.0.0 fixed (#1889). Any version
check against a stale process is therefore misleading on both counts.

Upgrade command: `uv tool install serena-agent@latest --force`
(`uv tool upgrade serena-agent` refuses when the version is pinned). Then
restart the affected `serena-backend@<port>.service` units.

### 6.3 Findings from the 2.0.0 conformance pass

- **F1 — `serena project create` exit code changed.** On 2.0.0 it exits **1**
  when the project already exists (1.7.0 exited 0, printing to stderr). Impact:
  none — `serenaCreate()` pre-checks `project.yml` and skips `create` entirely, so
  the re-enable path never reaches it.
- **F2 — `serena project remove` now exists** (see §5). Our disable path
  deliberately does not use it.
- **F3 — `health-check` writes `.serena/` into the working tree** (see §2.1).
- **F4 — `health-check` is not a clean gate for polyglot projects.** It fails on
  symbol-less languages (json/yaml/toml/markdown) because `textDocument/references`
  is unimplemented (`-32601`). A limitation, not a regression.
- **F5 — language-server table verified.** All 51 `EXTENSION_SERVERS` mappings are
  valid 2.0.0 IDs; zero invalid. See §3.
- **F6 — a bare `activate_project` can leave a single-language stub.** One project
  was created that way and held `language_servers: [markdown]`. Re-provision with
  `serena-provision --force` if it needs full coverage.
- **F7 — directory keying still basename-of-root** (see §2).
- **F8 — `initial_instructions` is exposed under `--context ide`** (§6.1).
- **F9 — unscoped `find_symbol` fails on a project whose tree contains symlinks
  leaving the root.** Reproduced on a project whose `skills/` directory held
  symlinks to a path outside the tree: `find_symbol` without `relative_path`
  ("searches entire codebase", `symbol_tools.py:118`) follows one out of the tree
  and raises `ValueError: '...' is not in the subpath of '...'`. Workaround: pass
  `relative_path`. Pre-existing (not upgrade-caused) but newly reachable; upstream
  is fixing it — changelog #2144 ignores symlinks for untrusted projects.
  `get_symbols_overview(relative_path=...)` and `search_for_pattern` are
  unaffected. **This class of failure reaches the router design**: any tool that
  walks a tree must not follow symlinks out of the project root.

### 6.4 Verified working

- All socket units load; `serena-mcp@<port>` serves 2.0.0; `initialize` returns
  the pointer instruction.
- `parseLanguageServers` / `parseRegisteredProjects` match 2.0.0 file shapes.
- Live per-language symbol queries verified for typescript and python projects.
